# _repair's SequenceMatcher(autojunk=False) has cubic-ish blowup on documents with many duplicate short lines (Priority 3 | Status: in_progress)

## Description
Found during round-2 adversarial review of PR #50 (tests+security lens, confidence 90, verified via direct benchmark).

PR #50 sets `autojunk=False` on the `SequenceMatcher` calls in `_repair` (and the top-level matcher) in `src/docspan/backends/google_docs/docs_request_builder.py` — required for this PR's own correctness fix (autojunk=True was silently misaligning nodes on documents with repeated short tokens, e.g. fenced code blocks). But this reintroduces difflib's classic worst case on inputs with many repeated short tokens — the same pattern that motivated the fix.

Benchmarked directly against N synthetic duplicate-text paragraphs:
- N=200 → 0.045s
- N=400 → 0.375s
- N=800 → 2.95s
- N=1500 → 19.2s

Growth is cubic-ish, not linear/quadratic. A document with a few thousand duplicate short lines or table cells (plausible for code-heavy docs or large tables) could hang push/pull for minutes.

Not blocking PR #50's merge — the correctness fix is required and this is a pre-existing tradeoff of the algorithm choice, not a regression introduced carelessly. But worth a follow-up: either bound the duplicate-run size before falling back to a cheaper heuristic, or cap total node count with a fast-path warning.

Filed as an agent acting on tstapler's behalf via the github:pr-ship skill, not tstapler's own words.
