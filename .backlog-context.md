# google-docs: a fenced code block in a list item or blockquote is unsplit or dropped (Priority 3 | Status: in_progress)

## Description
`block_code` is parsed in **three** places and #41 fixed only the top-level one.
Both remaining cases are pre-existing (byte-identical before #41) and both are
pinned by a test in #41 that asserts they are *still* broken, so they cannot be
mistaken for fixed.

## In a list item — unsplit, and concatenated onto the list text

`markdown_to_paragraph_parser.py` `_walk_list_items` never reaches the fixed branch;
a `block_code` child falls through to `_spans_from_inline`, which returns the raw
token including newlines.

```
md = "- Steps:\n\n  ```sh\n  make build\n  make test\n  ```\n"
→ one node, text = 'Steps:make build\nmake test'
```

Two defects: the fence content is glued onto the list text with **no separator**, and
#40 still fires — push 2 on an untouched file emits `deleteContentRange` + `insertText`
forever, so the paragraphs are destroyed and recreated on every sync and any comment
anchored to them dies each time.

A fenced command block under a numbered step is one of the commonest shapes in an
engineering doc.

## In a blockquote — dropped entirely, and push deletes it

`_walk_block_quote` has no `block_code` branch, so the lines never reach the target.
If the document already holds them, push **removes** them:

```
doc: ['intro', '> Note:', 'kubectl get pods', 'kubectl logs -f', 'tail']
md:  intro / > Note: / > ```sh / > kubectl get pods / > kubectl logs -f / > ``` / tail
→ 2× deleteContentRange; document after push: 'intro\n> Note:\ntail\n'
```

At least this one surfaces as `2 removal(s)` in the preview.

## Fix direction

Move the per-line split into a helper and call it from all three sites, rather than
inline in one branch. The blockquote case additionally needs a `block_code` branch
that prefixes each line the way `_prefix_node_text` does for quoted prose.

Delete `test_a_fence_in_a_list_item_is_still_unsplit` when this lands.

## Acceptance Criteria
0. [ ] A fenced code block inside a list item is split into one DocsParagraphNode per line, each monospace, and is not concatenated onto the list item's own text
1. [ ] A fenced code block inside a blockquote is preserved (not dropped) with each line carrying the correct '> ' (or nested '> > ') quote prefix
2. [ ] Pushing an unchanged document containing a listed or quoted code block emits zero requests (idempotence, mirroring issue #40's fix)
3. [ ] Pushing markdown with a quoted fenced block that already exists in the live document does not emit deleteContentRange for those lines
4. [ ] A fenced block nested inside a list item that is itself inside a blockquote is handled correctly (composition of both fixes)
5. [ ] Generated code-line nodes carry correct is_list_item/nesting_level metadata matching their surrounding list context
6. [ ] Existing top-level fenced-code-block behavior (issue #40) is unchanged after refactoring to the shared helper
7. [ ] The pinned regression test test_a_fence_in_a_list_item_is_still_unsplit is deleted and the stale 'known gap' docstring language is trimmed, per the test's own instructions
8. [ ] Behavior for a blank line inside a quoted fenced code block is an explicit, tested decision rather than an accidental side effect of prefixing
