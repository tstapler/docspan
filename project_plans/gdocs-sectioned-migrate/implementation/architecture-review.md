## Original Review (superseded blockers/concerns kept for record)

### Blockers (RESOLVED — see Repair History)

- [x] **Task 5.3 (`pull --to-sectioned` reassignment)** — Plan text says migration should "fall through into the now-updated `mapping` object (freshly loaded/sectioned) for the rest of that iteration's normal pull logic," but the pull loop in `src/docspan/cli/main.py:460` (`for mapping in mappings:`, where `mappings = config.mappings` per `main.py:438`) binds the local variable `mapping` to the *existing* `Mapping` instance for that iteration. `_apply_config_update` (Task 4.2) builds a **fresh** `Mapping(**{...})` and swaps it into `config.mappings` — this replaces the list element, but the already-bound loop variable `mapping` still references the old, non-sectioned object; Python does not re-read the list mid-iteration. `orchestrate_pull` (`orchestrator.py:420`) dispatches purely on `mapping.sectioned`, so the "ordinary `pull_sectioned` branch" the plan promises for the same invocation will not fire — `mapping.sectioned` is still `False` on the stale reference, and the subsequent call re-runs the non-sectioned pull path against a `local` path that migration just deleted (Task 3.2 removes the original file), producing a hard failure or silently wrong behavior instead of the described "ordinary sectioned pull layered on top."
  **Remediation**: Give `MigrationResult` an explicit `new_mapping: Optional[Mapping]` field (populated by `_apply_config_update`'s return value) and have Task 5.3's `pull()` code explicitly do `mapping = migration_result.new_mapping` (rebinding the loop variable) before falling through to the normal per-mapping dispatch, rather than relying on implicit "fall through." Add this rebinding as its own bullet in Task 5.3, and add an integration-test assertion (extending Testing Strategy item 6) that verifies dispatch actually reaches `pull_sectioned` in the same invocation, not just that a second pull outcome appears.

### Concerns (RESOLVED — see Repair History)

- [x] **Epic 4 / Task 4.1 (`_record_state` save semantics)** — `orchestrator._record_state`/`record_state` calls `state.save(state_path)` on every invocation when `save=True` (the default), and `orchestrate_push`'s existing sectioned path (`orchestrator.py:393`) already calls it once per section file with the default, so today's sectioned push already writes `sync-state.json` to disk N times per push. Task 4.1 says migration should call `_record_state` "once per new section file path... then remove the old single-file entry... before saving once," which reads as intending a single terminal `state.save()` — but doesn't say to pass `save=False` on the per-file calls, and if it doesn't, "saving once" is inaccurate (each call saves immediately, and the terminal single-file-removal edit needs its own explicit `state.save()` call, which `SyncState.update`/dict-delete alone won't trigger). This is a correctness-adjacent ambiguity for the rollback design specifically: Task 4.3's unwind assumes a clean "restore prior `SyncState` in-memory values captured before Task 4.1/4.2 ran," but if intermediate `_record_state` calls have already persisted partial state to disk (via `save=True` default) before a later step fails, the created-paths-list rollback must also re-persist the restored in-memory `SyncState` to disk, not just mutate it in memory — the current Task 4.3 wording ("restore prior `SyncState`... in-memory values") doesn't say it also writes them back out.
  **Remediation**: Task 4.1 should explicitly say `save=False` for the per-section `_record_state` calls, with exactly one `state.save(state_path)` call after the old entry is removed (matching the "saving once" intent literally); Task 4.3 should explicitly call `state.save(state_path)` as part of unwinding `SyncState`, not just restore the in-memory dict.

- [x] **Epic 3, Task 3.2 vs. requirements' "atomic swap"** — the task explicitly defers `os.remove(old_file_path)` until after state+config both succeed (a late revision noted inline in Task 4.3's own text), but Task 3.2's own numbered description still lists `os.remove(old_file_path)` as the second step, immediately after `atomic_replace_dir`, followed by three `_run_git` calls including the commit. This means the described sequence commits `git rm --cached old_file_path` (staging the deletion) while the *working-tree* file has already been removed per the original wording, contradicted by the "revise Task 3.2" aside buried in Task 4.3. As written, a reader implementing Task 3.2 top-to-bottom (without reading ahead to Task 4.3) will delete the file before state/config succeed, defeating the "restore by simple presence" rollback Task 4.3 depends on.
  **Remediation**: Move the deferred-`os.remove` revision out of Task 4.3's parenthetical and into Task 3.2's own numbered steps directly — Task 3.2 should stage `git rm --cached` (index-only) without deleting the working-tree file, and the actual `os.remove` should be an explicit sub-step of Task 4.2 (after config write succeeds), not implied by a forward reference.

- [x] **`MigrationResult` / `MigrationPreview` — return-type contract underspecified for two independent call sites** — the Architecture Summary states `migrate_sectioned` "must not call `typer.Exit` or print directly" and returns a `MigrationResult` "so the same function serves both entry points," but the Blocker above shows at least one field (the new `Mapping`) is missing from the described shape, and neither `MigrationResult` nor `MigrationPreview` is given a concrete field list anywhere in the plan (Architecture Summary calls it "outcome enum + per-section preview data + messages" without enumerating them). Since Task 5.1/5.2 (standalone CLI) and Task 5.3/5.4 (`pull --to-sectioned`) are two independent consumers built potentially in different work sessions, an implicit/underspecified contract is exactly the kind of interface-stability risk Lens 3's API-contract-design check flags — a consumer needing to change if the "implementation" (here, what fields exist) changes mid-epic.
  **Remediation**: Add a concrete dataclass sketch for `MigrationResult` (outcome enum values, `new_mapping`, `sections: List[MigrationPreview]`, `messages: List[str]`, `rolled_back: bool` or similar) to the Architecture Summary before Epic 5 starts, the same way the plan already gives a concrete signature for `migrate_sectioned` itself.
