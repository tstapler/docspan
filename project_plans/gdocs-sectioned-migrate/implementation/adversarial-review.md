## Original Review (superseded blockers kept for record)

### Blockers (RESOLVED — see Repair History)
- [x] **Task 3.2 vs. Task 4.3 disagree on when `os.remove(old_file_path)` happens, and neither ordering actually works.** Architecture Summary step 5 and Task 3.2 both remove the original file *before* the single migration commit (swap → remove → `git add`/`git rm --cached`/`commit`), then step 6/Task 4.1-4.2 write `SyncState`/config *after* that commit has already landed. But Task 4.3's rollback design says to "revise Task 3.2 to defer `os.remove(old_file_path)` until after state+config both succeed... so rollback can restore it by simple presence." Both can't be true: (a) if removal+commit happens first (as 3.2/Architecture Summary state), a state- or config-write failure afterward requires *undoing a git commit* (`git reset --hard`/`git revert`) to restore the old file — something `_rollback` (Task 4.3) never actually describes doing, it only talks about deleting new files and restoring the old one from a kept-aside copy; (b) if removal is deferred past the commit (as 4.3 proposes), the single migration commit no longer contains the delete, so it's only an "add new files" commit — which breaks the Pattern Decision's foundational claim that history preservation and `git revert`-as-rollback both depend on one commit containing "delete original + add all sections." Recommendation: pick one ordering, and if it's (a), add an explicit `_rollback` step that runs `git reset --hard <pre-migration-HEAD>` (or `git revert`) when failure occurs after the commit — don't leave "restore by simple presence" as the only described mechanism when the file has actually already been deleted-and-committed.
- [x] **No BaseException-safe rollback for Ctrl-C.** Task 5.2 explicitly promises an "in-progress `[yellow]migrating[/yellow]` line... (Ctrl-C checkpoint)," implying the design intends migration to be interruptible mid-flight, but no task specifies catching `KeyboardInterrupt`/`SystemExit` (as opposed to `Exception`) around the pipeline to trigger `_rollback`. If the pipeline's failure handling is `except Exception`, a Ctrl-C during `_commit_swap` (after `git add`/`git rm --cached` have staged changes but before `commit` returns) leaves the git index in a half-staged state with no automatic unwind. Recommendation: wrap the pipeline in `try/except BaseException` (or an explicit `finally`-based unwind) and add a test that simulates a `KeyboardInterrupt` raised mid-`_commit_swap`.

## Concerns
- [ ] **No timeout/retry/error-wrapping around the live Google Docs API fetch.** `_split_live` (Task 2.1) calls `client.get_document(doc_id)` with no mention of retry-on-transient-failure, rate-limit handling, or wrapping the raw exception in `MigrationError` — every other failure path in this plan gets a distinguishable `MigrationError`, but a network blip or expired OAuth token here would surface as a raw traceback instead of the "friendly-message fast exit" convention the rest of the command follows. Recommendation: wrap the fetch call and map known failure classes (auth, network, 404) to `MigrationError` messages, consistent with `_run_git`'s treatment of git failures.
- [ ] **`_run_git`'s timeout is an unfilled placeholder (`timeout=<small>`).** For a large repo, `git status --porcelain`, `git add <section-dir>`, or `git commit` (with hooks) can legitimately take longer than a "small" timeout tuned for a quick `rev-parse`. A one-size-fits-all short timeout risks spurious `MigrationError`s (or worse, killing `git commit` mid-write) on exactly the large-doc repos this feature targets. Recommendation: size the timeout per call site (rev-parse/status can be short; add/commit needs a longer budget) and decide before implementation, not as a TODO.
- [ ] **`pull --to-sectioned` creates an unsolicited git commit as a side effect of `pull`.** Every other `pull` invocation in docspan is read-only with respect to git (it writes files, not commits). Task 5.3 has this flag silently create a full migration commit *before* pull's own write phase, with no confirmation step — a user who reflexively re-runs `pull --to-sectioned` (e.g., in a script or muscle memory) gets a new git commit each time it applies to a newly-added non-sectioned mapping, which is a bigger behavioral surprise than the CLI's own explicit `migrate-sectioned` command carries. Recommendation: at minimum, have `pull --to-sectioned` print the same commit-creation notice the standalone command does, and consider gating it behind an explicit confirm unless `--yes`/non-interactive is set.
- [ ] **Title-matching drift detection in `_zip_sections` (Task 2.3) doesn't specify normalization.** Live-doc heading text (Docs API) and local-markdown heading text may differ in smart quotes, trailing whitespace, or Unicode normalization even when semantically unchanged, which would trip the "remote diverged" abort on a doc that hasn't actually diverged. Recommendation: specify exact/normalized comparison rules (e.g., `.strip()` + NFC normalization) and add a unit test for a whitespace-only difference to confirm it does *not* false-positive.
- [ ] **Requirements' Success Metric and the plan's actual printed/tested flags disagree without reconciliation.** `requirements.md`'s Success Metrics section still reads `git log --follow -C --find-copies-harder` / `git blame -C -C`, but Task 3.3's commit-message tip and Task 3.5's integration test both use `-C20%` (three copies for blame) and drop `--find-copies-harder` entirely. This looks like an intentional spike-verified simplification (per `research/stack.md`), but `requirements.md` was never updated to match, so a future reader diffing the two docs would reasonably conclude the implementation is under-delivering on the stated bar. Recommendation: update `requirements.md`'s Success Metric to the flags actually verified/shipped, or add an explicit note pointing to the research spike as the superseding source of truth.

## Minors
- Placeholder `heading_id` scheme (`"__migrated-{index}__"`) is documented as self-healing on next pull, but there's no idempotency test for running `migrate-sectioned` a second time against a mapping that's already sectioned (pre-flight check should reject it, per Task 5.1/pre-flight — worth a one-line explicit test rather than relying on inference from the pre-flight check description).
- Byte-identical section content claim (Pattern Decisions, git-history preservation row) doesn't address line-ending normalization (CRLF/LF) or trailing-newline handling that might exist elsewhere in docspan's write path — if any normalization happens on read/write outside `_stage_sections`, "byte-identical" could silently not hold. Worth a quick grep-and-confirm before implementation, not necessarily a new task.
