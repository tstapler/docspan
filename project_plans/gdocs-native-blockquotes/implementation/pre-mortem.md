# Pre-mortem: gdocs-native-blockquotes
**Date**: 2026-08-17

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `BLOCKQUOTE_BORDER_MARKER` empirically chosen in the one-person Epic 0 spike doesn't round-trip identically across all accounts/locales — Docs normalizes color representation (e.g. theme color vs. RGB hex), rounds `indentStart`/border `width` to a slightly different point value, or a Workspace admin policy strips custom borders — so `_detect_blockquote_depth`'s sub-field comparison silently fails to match on re-fetch for some subset of users. | A pulled Doc that was pushed with `>` renders as a plain paragraph with no `>` prefix at all (blockquote structure silently dropped, not even falling back to legacy literal text) — worse than today's baseline, and non-obvious because it isn't a crash, just missing markdown. | Before ship, run Epic 0's spike against more than one Google account/Workspace domain (not just the implementer's), and assert on exact re-fetched values rather than assuming one clean run generalizes; add the committed re-runnable fixture test (already planned in Story 0.1 task 6) to CI so drift is caught continuously, not just once. | P1 |
| 2 | The comment-loss "one-time migration" cost is invisible in any non-interactive push (CI/CD pipeline, scripted `docspan push` without a human reading dry-run output) — `style_upgrade` warnings only surface via `push --dry-run` and terminal-rendered `render_high_risk`/`render_churn_note` text, with no exit-code signal or machine-readable channel. | Weeks after ship, a team using docspan in CI to auto-sync docs discovers their Google Doc comment threads vanished on old blockquote paragraphs, with no record of why — support ticket, not caught by anyone watching dry-run output. | Add a non-zero/distinct exit status or a `--fail-on-comment-loss` flag (or at minimum a structured warning count in stdout that scripts can grep) for pushes that trigger `style_upgrade`/comment-loss reasons, so CI-driven consumers have a detectable signal, not just pretty terminal text; document this explicitly in `docs/backends/google-docs.md`. | P1 |
| 3 | Story 1.3's `_structural_score` fix is conditional ("if needed, only if Task 1 shows a gap") and gated on a read that "has not yet been performed as of this planning pass" (per requirements.md Feasibility Risks and plan.md Unresolved Question 5) — if the implementer's read is rushed or the scoring gap is subtle (e.g. it partially but not fully weighs style), `_repair`'s cross-document content-key pooling could misclassify a blockquote and a non-blockquote paragraph with identical text, applying the wrong style to the wrong paragraph. | A pushed Doc shows blockquote styling (border/indent) on a paragraph the author never wrote with `>`, or vice versa — a plain paragraph loses its border on a later push — reported as "random" incorrect formatting that doesn't correlate with any recent edit to that specific paragraph. | Make Story 1.3's regression test (two same-text paragraphs, one blockquote one not, in the same document) a hard requirement gating Epic 2 merge, not an optional follow-up task; do not treat "if needed" as license to skip the code read — require the read's finding to be written down in the PR description before Epic 2 lands, per this codebase's own evidence-based-claims discipline. | P1 |
| 4 | Unresolved Question 4 (undocumented `batchUpdate` payload size cap) is explicitly deferred as "not blocking ship" — but the migration design (Step 4) means a document with many legacy blockquotes migrates *all of them in a single push* the first time any one paragraph changes, which is exactly the scenario most likely to hit a payload cap, and it hits hardest for the power users this feature is meant to help (heavy `>` users). | A push that used to succeed now fails outright with an API error on a large, blockquote-heavy document, blocking the user's workflow entirely — the opposite of the intended fix, and it lands specifically on the user population this feature targets. | Before ship, test push against a synthetic document with a large number (50-100+) of legacy blockquote paragraphs to empirically measure whether a single push's migration batch approaches Google's `batchUpdate` limits; if it does, add request-batching/chunking to the existing push pipeline rather than shipping this as a known-but-undocumented-severity risk. | P2 |
| 5 | The list-in-quote / quote-in-list indent-stacking "additive by construction" claim (Story 2.6) and the table-cell inheritance question (Story 2.4, Unresolved Question 3) are each verified against only one live-Doc spike scenario, not the cross product of nesting depths, list types, and cell contexts that real LLM-authored markdown will produce (e.g., a quote containing a nested list containing another quote). | A Doc with a moderately complex nested structure (list inside quote inside table cell, or double-nested quote-with-list) renders with visually broken/overlapping indentation, or a code block's language marker is lost, in production — not caught by the plan's four required round-trip cases (plain/nested/list-in-quote/code-in-quote), which don't include 3+-way compositions. | Explicitly scope the round-trip test matrix to state which N-way compositions are *not* covered (documented as an accepted gap in `docs/backends/google-docs.md` Limitations, per the existing project convention), and add at least one 3-way composition test (e.g., quote containing a list containing a code block) as a stretch goal before ship rather than discovering the gap from a user report. | P2 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Extend Epic 0 Story 0.1 to run the marker-write/re-fetch spike against more than one Google account/Workspace domain, and land the committed fixture as a CI-run regression test (not just a one-time code comment) before Epic 1/2/3 begin.
- [ ] Failure #2 — Add a story to Epic 4 (or extend Story 4.1) for a machine-readable/CI-detectable signal (exit code, structured output, or opt-in `--fail-on-comment-loss` flag) when a push triggers `style_upgrade`/comment-loss, so non-interactive pipelines aren't silently exposed to comment loss.
- [ ] Failure #3 — Change Story 1.3 acceptance criteria from "if Task 1 shows a gap" to a hard requirement: the regression test (same-text blockquote vs. non-blockquote paragraphs) must pass and be committed before Epic 2 can merge, with the `_structural_score` read's finding recorded in the PR description.
