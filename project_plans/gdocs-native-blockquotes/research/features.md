# Research: gdocs-native-blockquotes — feature landscape

## 1. Current push-side behavior (`markdown_to_paragraph_parser.py`)

Source: [`src/docspan/backends/google_docs/markdown_to_paragraph_parser.py`](../../../src/docspan/backends/google_docs/markdown_to_paragraph_parser.py)

- `BlockQuoteTokenConverter.convert()` (L528-532) dispatches straight to `_walk_block_quote(token)` (L363-401).
- `_walk_block_quote(token, quote_depth=1)`:
  - Builds `prefix = "> " * quote_depth`.
  - `paragraph` child: inline-parses spans, builds a plain `DocsParagraphNode(style="NORMAL_TEXT", ...)`, then runs it through `_prefix_node_text(node, prefix)`.
  - `list` child: recurses into `_walk_list_items(child, nesting_level=0)` (list nesting always restarts at 0 inside a quote — no compounding with quote depth today), then prefixes **every** resulting list-item node with the same literal quote prefix.
  - `block_code` child: routes through `_nodes_from_code_block(child)` (no `emit_language_marker`, so a fence inside a quote never carries a language marker — this is called out explicitly in `_nodes_from_code_block`'s docstring, L282-285), then prefixes each resulting line node.
  - `block_quote` child (nesting): recurses with `quote_depth + 1` — deeper nesting is *not* prefix-wrapped again at this level; the recursive call handles its own (larger) prefix internally, so a `>` line inside a `> >` block only ever gets one `"> > "` prefix total, not doubled.
  - `blank_line` child: skipped (`continue`) — no node emitted, so a blank line inside a quote produces nothing (not even an empty quote-marker line), unlike an interior blank line in a fenced code block (see below).
  - Anything else (e.g. a table): silently dropped — comment at L399-400 says nested tables inside a block quote are "rare; fall back to skipping rather than mis-rendering."
- `_prefix_node_text(node, prefix)` (L345-360): returns a **copy** of the node with `prefix + node.text` as the new text, and — only if `node.spans` is non-empty — prepends a new unstyled `TextSpan(text=prefix)` to `spans`. If `spans` was empty (unstyled plain text), spans stay empty and only `.text` carries the prefix; there's no span for the prefix itself in that case. This is the exact literal-text scheme the requirements doc's Baseline section describes: no Docs paragraph style ever changes, `style` stays `"NORMAL_TEXT"` (or whatever the child converter set), `is_list_item`/`nesting_level` pass through unchanged from the wrapped node.
- Blank line *inside a fenced code block that is itself inside a quote*: `_nodes_from_code_block` emits a node with `text=""` for that line (spans `[]`); `_prefix_node_text` then turns that into `text="> "` (non-empty) — this is called out explicitly in `_walk_block_quote`'s own comment (L386-391) as deliberate, so the blank interior line survives push/pull instead of being dropped by the paragraph-projection rule that drops nodes with `text == ""`.
- Net effect: every markdown construct inside a quote (`paragraph`, `list`, `block_code`, nested `block_quote`) becomes one or more ordinary `DocsParagraphNode`s whose *only* blockquote signal is a literal `"> "`-repeated prefix baked into `.text` (and, when styled, into a synthetic leading `TextSpan`). Nothing about `style`, `is_list_item`, `nesting_level`, or any paragraph-style field is affected by being inside a quote.

### Fidelity bar this sets for the new implementation
A new native-styling implementation must, for the same four cases (plain paragraph, nested quote, list-in-quote, code-in-quote), preserve:
- The **same text content** post-quote-prefix-removal (i.e., the underlying paragraph/list-item/code-line text, unprefixed).
- The **same document paragraph count and per-node shape** the diff engine already expects (one `DocsParagraphNode` per rendered line, code lines one-per-line via `_nodes_from_code_block`, no language marker for quote-nested fences).
- List nesting inside a quote restarting at `nesting_level=0` (current behavior — not compounded with quote depth).
- An interior blank code line inside a quoted fence still round-tripping (today via the non-empty `"> "` text trick; the new design needs an equivalent non-drop mechanism once the prefix text is gone — likely relying on `is_blockquote`/`quote_depth` alone keeping the node non-blank-shaped, or an explicit carve-out in `nodes_to_markdown.py`'s blank-line handling).
- Blank lines directly inside a quote (not inside a nested fence) continuing to disappear (current: `blank_line` child skipped entirely).
- Nested-table-in-quote continuing to be silently dropped (unsupported, unchanged).

## 2. Pull-side parsing today (`docs_structure_parser.py`)

Source: [`src/docspan/backends/google_docs/docs_structure_parser.py`](../../../src/docspan/backends/google_docs/docs_structure_parser.py)

- `DocsParagraphNode` (L148-188) fields today: `style`, `text`, `is_list_item`, `nesting_level`, `start_index`, `end_index`, `spans`, `render_prefix`, `is_native_checkbox`, `precedes_structural_element`, `heading_id`. No blockquote-related field exists.
- `DocsStructureParser.parse()` → `_parse_paragraph()` (L518 onward) reads `paragraph.get("paragraphStyle", {})` (L523) but only ever pulls `namedStyleType` out of it (L524). Confirmed via `grep -n "indentStart\|borderLeft\|paragraphStyle"` over the whole file: the only other paragraphStyle-related hit in the file is the comment at L183 about `headingId`, and `paragraph_style` itself is never queried for `indentStart` or `borderLeft` anywhere. **Confirmed: no code today reads `indentStart`/`borderLeft` at all** — matches the requirements doc's stated expectation exactly.
- Consequence for the new design: `_parse_paragraph` will need a new step that inspects `paragraph_style.get("indentStart")` and `paragraph_style.get("borderLeft")` against the docspan-owned marker values, and sets `is_blockquote`/`quote_depth` on the resulting node — entirely new code, no existing precedent to extend other than the `namedStyleType` read it sits beside.

## 3. Pull-side rendering today (`nodes_to_markdown.py`)

Source: [`src/docspan/backends/google_docs/nodes_to_markdown.py`](../../../src/docspan/backends/google_docs/nodes_to_markdown.py)

- `_build_pull_registry()` (L508-515) registers exactly five dispatch keys: `table`, `heading`, `list_item`, `paragraph`, `image`. `_dispatch_key()` (L264-274) synthesizes the key from `node.style`/`node.is_list_item`/node type — there is no blockquote-aware branch anywhere, confirming the requirements doc's Baseline claim by direct grep/read.
- `render_nodes_to_markdown()` (L521-534) is a two-stage pipeline: **stage 1** is `_group_code_runs(nodes)`, producing a list of `("node", node)` passthroughs and `("code", lang, code_nodes)` runs; **stage 2** dispatches each passthrough node through `_PULL_REGISTRY` by `_dispatch_key`. Code runs bypass dispatch entirely and go straight to `_render_code_group`.
- `_group_code_runs` (L339-399), read in full:
  - Walks `nodes` with index `i`. At each position, first checks whether the current node `_is_language_marker` (a specific literal-marker shape: `NORMAL_TEXT`, not a list item, text starts with `FENCE_MARKER`, and — if it has spans — exactly one span with no bold/italic/link/monospace). If so and the next node `_is_pure_code_line`, the marker is consumed and `lang` is captured from its text; if instead the next node is a single blank-code-line with no code following it, that's treated as an explicit **empty fence** shape and emitted directly as `("code", lang, [])`.
  - Otherwise (or after consuming a marker), if the node at `start` `_is_pure_code_line`, a run is grown: consecutive pure code lines extend the run; a *contiguous span* of blank-code-lines is tentatively absorbed only if **another pure code line follows** it (look-ahead via inner `while k`), otherwise the run stops before the blank lines.
  - `_is_pure_code_line`/`_is_blank_code_line`/`_is_language_marker` **all** require `not node.is_list_item`, and (implicitly, since blockquote content today is just `NORMAL_TEXT` prefixed paragraphs) they say nothing about blockquote-ness — under the current scheme a quoted code line's text is `"> ```lang"`-shaped or `"> code"`-shaped, which does **not** match `_is_pure_code_line`'s exact-one-monospace-span check cleanly today for the marker (the marker is never emitted for quoted fences per `_nodes_from_code_block`'s docstring) — so today a quoted fenced code block is *not* grouped into a `code` run at all; each quoted code line renders one at a time via the ordinary `paragraph` dispatch key, with its literal `"> "` prefix intact as plain text. This is implicit confirmation that "code block inside a quote" currently gets zero special pull-side handling — it "works" purely because the prefix text round-trips byte-for-byte through the plain-paragraph path.

### What a `_group_blockquote_runs` stage must reconcile with `_group_code_runs`
- **Ordering**: `_group_code_runs` currently runs first and is the only grouping stage; `render_nodes_to_markdown` iterates `_group_code_runs(nodes)`'s output directly. Introducing `_group_blockquote_runs` means deciding composition order — e.g. run blockquote-grouping first (so quote runs are opaque units to code-grouping, and code-grouping is invoked *per-quote-run* on the run's contained nodes to recover a fence nested inside), or run code-grouping first over the raw node stream and then have blockquote-grouping consume `("code", ...)` tuples as opaque members alongside `("node", ...)` ones. The former (nest code-grouping inside blockquote-grouping) is more consistent with today's fidelity, since a quoted fence never triggers the top-level marker-based grouping anyway (no marker emitted) — but if the new design *does* start emitting language markers for quoted fences (a design decision, not yet made), then order matters a lot: code-grouping's `_is_pure_code_line`/`_is_language_marker` checks would need `is_blockquote`/`quote_depth` added to their exclusion checks (today only `is_list_item` is excluded), or false-positive fence detection could span across a quote boundary.
- **New predicate shape needed**: today's code-line predicates are keyed on exact node shape (`style`, `is_list_item`, `spans` count/monospace). A parallel `_is_blockquote_line`-type predicate keyed on the new `is_blockquote`/`quote_depth` fields is straightforward to add, but the interaction case explicitly flagged in the requirements' Rabbit Holes/Feasibility Risks (a fenced code block *inside* a quote) means the two grouping passes cannot be fully independent: the emitted markdown for that case must be `"> ```lang" / "> code line" / "> ```"` — i.e., blockquote-prefixing wraps *around* the rendered fence lines, meaning `_render_code_group`'s output lines each need the quote prefix applied after code-rendering, not before. This argues for blockquote-grouping being the *outer* stage that recursively re-invokes code-grouping (and future prose rendering) on its inner node list, then prefixes every resulting rendered line with `"> " * quote_depth`.
- **Risk if not composed carefully**: a naive single flat pass that tries to match both "is this a code line" and "is this a blockquote line" predicates at once will likely mis-group at the boundary where a quote starts/ends mid-fence, or where a nested quote's own depth changes line-to-line (not possible within one fence, but relevant for two adjacent quotes at different depths — see edge cases below).

## 4. Edge cases the design must explicitly handle

1. **Quote directly adjacent to a non-quote paragraph (no blank line between them in the Doc).** Today, `_walk_block_quote` only prefixes lines that are markdown children of a `block_quote` token; a following sibling `paragraph` token gets no prefix and dispatches through `ParagraphNodeRenderer`. On pull, nothing currently marks a paragraph's "quote-ness" positionally — CommonMark's own grammar requires no blank line to separate a quote from the next block only when the next line does *not* start with `>` (lazy continuation applies within a quote, not across it into plain text), so today's literal-prefix scheme relies on the text prefix itself, not adjacency, to signal where the quote ends. The new design must ensure `is_blockquote`/`quote_depth` (not paragraph adjacency) alone determines quote membership per-node, so a non-quote paragraph immediately following a quote paragraph (no blank line) renders correctly as ordinary text with no leaked `>` and no incorrectly-merged grouping.
2. **Quote immediately followed by another quote at a different depth (no blank line).** E.g. `> a\n> > b` (a depth-1 line directly followed by a depth-2 line, no blank line, valid CommonMark). Since indentation is scaled per-depth, the new pull-side grouping must key runs by `quote_depth` per-node (not just `is_blockquote`), and must reconstruct each line's own `"> " * quote_depth` prefix independently in the same visual run, rather than assuming one border/indent value read from the *first* line of a contiguous "blockquote-ish" run applies to the whole run.
3. **Empty quote line (`>` with nothing after).** Currently: this parses to mistune as either a `paragraph` child with empty inline children, or a `blank_line` child of the `block_quote` token depending on mistune's exact tokenization; `_walk_block_quote`'s `blank_line` branch drops it outright (no node), while a genuinely-empty `paragraph` child would produce a node whose `_text_of(spans).strip()` is `""`, then get prefixed to `"> "` by `_prefix_node_text` — non-empty, so it survives blank-paragraph-dropping. The new design needs an explicit decision: does an empty quote line still need to emit *a* node (so pull can reconstruct the empty `>` line), given there's no longer a literal-text trick to keep it non-blank? Likely needs a sentinel (e.g., the node carries `is_blockquote=True` with `text=""`, and blank-drop logic is changed to check text-emptiness only for *non-blockquote* nodes).
4. **A quote containing a table.** Confirmed unsupported in markdown parsing today — `_walk_block_quote`'s only handled child types are `paragraph`, `list`, `block_code`, `block_quote`, `blank_line`; anything else (including `table`) falls through with no `elif` clause and is silently skipped, per the explicit comment at L399-400. This stays out of scope per the requirements doc's "Out of Scope" section (no change to what a quote can contain) — the new implementation should preserve this drop-silently behavior for tables inside quotes, not attempt to add table support.
5. **Mixed nesting: list containing a quote, vs. quote containing a list.**
   - *Quote containing a list* (`> - item`) is handled today (`_walk_block_quote`'s `list` branch, `nesting_level=0` restart, whole-line quote-prefix applied after list-rendering) — this is explicitly in scope per the requirements doc.
   - *List containing a quote* (`- > note`) has **no current code path** in `markdown_to_paragraph_parser.py`: `_walk_list_items` (L207-252) only recognizes `paragraph`, `block_text`, `list`, and `block_code` children of a `list_item` — a `block_quote` child falls into the generic `else` branch (L243-244: `spans.extend(_spans_from_inline([child]))`), which does not recognize `block_quote` as an inline token type and will most likely fail to extract meaningful text (or extract nothing, since `_spans_from_inline` has no `block_quote` case and falls through to its own generic branch trying `.get("children")` on a block-level token whose children are block-level, not inline — likely mis-renders or drops the nested quote's content). This is not mentioned as in- or out-of-scope explicitly in the requirements doc's Scope section, but the doc's own two mixed-nesting risk (Rabbit Holes: "quote containing a list") is one-directional — the reverse direction (list containing a quote) is not addressed by the requirements and should be flagged to the planning phase as an open question: is "list item containing a `>` note" in scope, and if not, does it need to keep failing exactly as it silently mis-renders today (no regression), or does dropping the literal-prefix scheme change its failure mode?

## 5. Prior art: how other tools represent blockquotes/callouts via indent+border (or otherwise)

1. **Google Docs API itself (native primitive)** — Google's own Docs API example for `UpdateParagraphStyleRequest` sets `borderLeft` (a `ParagraphBorder` with `color`/`dashStyle`/`padding`/`width`) combined with indentation as the standard way to produce a blockquote-like visual, because Docs has no dedicated "blockquote" paragraph type (confirmed independently by Google's own community forum: "I don't believe blockquotes are supported yet" — only indent/border tricks exist). This validates the requirements doc's chosen approach (`indentStart` + `borderLeft`) as literally the only mechanism Google itself uses/recommends for this look. ([`ParagraphStyle` API docs](https://googleapis.dev/java/google-api-services-docs/latest/com/google/api/services/docs/v1/model/ParagraphStyle.html))
2. **Pandoc's DOCX reader** — uses a heuristic based on relative paragraph indent to decide whether to synthesize a `<blockquote>` on the way *into* its AST: a paragraph is treated as a blockquote candidate when `relativeIndent > 0` and it isn't a list-style paragraph (`transform = if elem listParagraphStyles then id else if relativeIndent pPr > 0 then blockQuote else id`, roughly). This is the closest existing precedent to docspan's pull-side plan of inferring `is_blockquote` from `indentStart` on parse, rather than from an explicit document-model field — reinforcing the need for a *distinctive marker* (docspan's plan to use an unusual, docspan-owned border/indent combination) so ordinary user-applied indentation isn't misidentified as a quote. ([pandoc issue discussing this heuristic](https://github.com/jgm/pandoc/issues/8836))
3. **Notion's block model** — sidesteps the whole indent/border-heuristic problem by having a genuine first-class `"type": "quote"` block distinct from `"paragraph"`, so no visual-styling heuristic is needed at all; Notion's newer "Enhanced Markdown" export format goes further and represents its distinct `callout` concept with an explicit `<callout icon="…" color="…">` XML-like tag rather than reusing `>` for callouts. This is the sharpest contrast with Google Docs' situation: Notion's API has structural affordances docspan's target (Google Docs' flat paragraph+styling model) simply lacks, which is exactly why docspan must fall back to Pandoc's style of visual-marker inference rather than reading a semantic field. ([Notion Enhanced Markdown docs](https://developers.notion.com/guides/data-apis/enhanced-markdown))

## Summary of confirmed facts (for planning)

- `_walk_block_quote`/`_prefix_node_text` never touch `style`, `is_list_item`, or `nesting_level` — only `.text`/`.spans` carry the current quote signal, confirmed by full read of [markdown_to_paragraph_parser.py](../../../src/docspan/backends/google_docs/markdown_to_paragraph_parser.py) L345-401.
- `DocsParagraphNode` and `_parse_paragraph()` never read `indentStart`/`borderLeft` today — confirmed by grep across [docs_structure_parser.py](../../../src/docspan/backends/google_docs/docs_structure_parser.py) (only hit besides a docstring mention of `headingId` is the `namedStyleType` read at L524).
- `nodes_to_markdown.py`'s pull registry has exactly 5 dispatch keys and one grouping stage (`_group_code_runs`); no blockquote-aware code exists anywhere in the pull path, confirmed by full read of `_group_code_runs` (L339-399) and the registry (L508-515).
- A quoted fenced code block today gets **no** code-run grouping at pull time at all (each line dispatches as plain `paragraph` with its literal prefix intact) — the new `_group_blockquote_runs` will be the first time quoted code gets any structural grouping, which is new functionality, not a refactor of existing behavior.
- `_node_key`/`_content_key`'s existing split (full identity vs. restyle-safe identity) in [docs_request_builder.py](../../../src/docspan/backends/google_docs/docs_request_builder.py) L225-370 is precisely the established pattern (already used for `render_prefix` and image `src`) that `is_blockquote`/`quote_depth` should follow: include in `_node_key`, exclude from `_content_key`.
- `updateParagraphStyle` call sites at insert (L2508) and restyle (L2704) both currently write only `{"namedStyleType": ...}` with `"fields": "namedStyleType"` — extending the `fields` mask and paragraph-style payload at both sites is a straightforward, well-precedented extension of an existing pattern, not new architecture.
