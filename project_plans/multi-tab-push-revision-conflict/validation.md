# Validation: Multi-Tab Push Revision Conflict

## Adversarial Review

### Challenge 1: Is RC1 actually triggered by the reported scenario?

The reported scenario is "change content in most of them, then push". If content changed,
`plan.requests` would be non-empty, so the `if plan.requests:` condition in pass 2 would be
True, and the re-fetch would happen correctly. RC1 only triggers when `plan.requests=[]`.

**Response**: True — if the user only changed content (no style reconciliation needed), RC1
wouldn't trigger. However:
- Style requests are generated by `_document_style_requests(plan.whole_doc, pageless)`, which
  reflects the document's current pageless/pages toggle, not the markdown content. A doc could
  have `plan.requests=[]` (content already in sync) but `style_requests=[...]` (pageless mode
  needs toggling).
- The reported 11-file run had 2 failures. The reporter says "re-running the same command
  afterwards succeeded". This re-run behavior is consistent with RC1: after the failed pass 2,
  pass 1's style changes ARE in the doc. On re-run, `style_requests=[]` (already applied), so
  `first_pass_requests=[]`, pass 1 doesn't write, pass 2 uses `plan.doc` with the current
  (latest) revisionId → succeeds.
- RC2 (cross-mapping eventual consistency) is also plausible but requires Google API
  read-after-write lag, which is not guaranteed.
- Either way, fixing RC1 is clearly correct (it IS a bug regardless of which case actually
  triggered the report). RC2's retry is also clearly correct defensive code.

### Challenge 2: Will the retry in Fix 2 re-upload images unnecessarily?

If a push with images fails on the `batch_update` after uploading temp Drive files, a retry
via `_build_push_plan` would try to re-upload the same images.

**Response**: Acknowledged in the plan as a known complication. Three mitigations:
1. The 400 "requiredRevisionId" error is detected at `batch_update` time, AFTER `_build_push_plan`
   has already run. The temp files are uploaded inside `_build_push_plan`. A retry via Fix 2
   would call `_build_push_plan` again, attempting another upload.
2. To avoid double-upload: clean up the first attempt's temp files before calling
   `_build_push_plan` again. `_cleanup_plan_temp_uploads(plan)` already exists for this.
3. If this complexity is unacceptable, Fix 2 can be scoped to only retry when
   `plan.temp_drive_file_ids == []` (no images uploaded in this push). This covers the
   most common case (text-only pushes) and avoids the image double-upload issue.

### Challenge 3: Does the test for RC1 (Test A) actually exercise the code path?

The test needs to reach `_execute_push` in a state where `plan.requests=[]` but
`style_requests` is non-empty. `style_requests` comes from `_document_style_requests(plan.whole_doc, pageless)`.

**Response**: `_document_style_requests` is mockable at the backend level. Set `pageless=True`
on the mapping and mock `plan.whole_doc["documentStyle"]["useCustomHeaderFooterMargins"]` to
the wrong value, which will generate a style request. Alternatively, mock
`_document_style_requests` directly to return a non-empty list. Test A is feasible.

### Challenge 4: Fix 1 adds an extra GET on every style-only push. Is this a performance concern?

**Response**: Style-only pushes are rare (content already in sync, only pageless toggle
needed). The extra GET is the correct behavior; the current code path that skips it is wrong.
The performance impact is negligible and bounded by the same `_with_backoff` retry mechanism
as all other GETs.

### Challenge 5: Does the multi-mapping cross-tab scenario (RC2) require changes to the CLI or orchestrator?

**Response**: No. The retry belongs in `_execute_push` because that's where the `HttpError`
is caught and translated to a `PushResult`. The CLI and orchestrator have no special knowledge
of revisionId conflicts; adding retry there would require threading state that currently doesn't
need to exist at that level. Keeping the retry in `_execute_push` preserves the existing
separation of concerns.

## Validation Verdict

- Fix 1 is correct, minimal-risk, and should be shipped.
- Fix 2 is correct but has the image-upload complication; scope it to image-free pushes in v1
  or accept the re-upload cost with a cleanup step before retry.
- Fix 3 (error message) should be shipped alongside Fix 1 regardless of Fix 2's status.
- Tests A, B, C are feasible and should accompany the respective fixes.
- No regressions to existing `status="conflict"` behavior expected, since the retry only fires
  on the first attempt and genuine external conflicts (where both attempts fail) still return
  `status="conflict"`.
