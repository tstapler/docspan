# Pre-mortem: gdocs-sectioned-sync
**Date**: 2026-08-13

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Task 7.4.1 "re-tunes" `DiffTooExpensive` thresholds to accommodate a large reassembled multi-section doc, but `_MAX_COMPARISON_CELLS`/`_MAX_DUPLICATE_RUN` (`docs_request_builder.py:43-45`) are module-level globals shared by every `_bounded_opcodes` call site (`_opcodes`, `_repair`, `_align_for_styling`) with no per-context override — there is no such thing as "the sectioned threshold" separate from "the single-file threshold." Loosening them to let a legitimate large sectioned doc through silently raises the pathological-duplicate-content ceiling for every existing single-file mapping too, directly violating the requirement "existing mappings are completely unaffected." | An existing, previously-fine single-file mapping (e.g. a doc with a large table of short repeated cells) starts producing a slow push or a mispaired-heading regression weeks after the sectioned feature ships, with no sectioned mapping anywhere near it — looks unrelated to this project in bisection. | Before Epic 7 lands, explicitly decide whether thresholds are actually global-and-shared (in which case Task 7.4.1 must prove that a *realistic* concatenated multi-section fixture never approaches the current single-file-tuned ceiling, no retuning needed) or whether `_bounded_opcodes` needs a `context`-scoped threshold parameter. Add an explicit regression test asserting single-file push behavior against the *pre-project* threshold values is unchanged. | P1 |
| 2 | The Task 3.2.2 design spike lands "no-go" (accept `heading_id` churn on reorder) but Story 7.3 and downstream code only assert this at the unit-test level against synthetic manifests — the plan never validates that "re-resolve cross-section anchors post-push" (the stated mitigation) is actually implemented anywhere. `heading_anchors.py` resolution is mentioned only for pull-side rendering (Unresolved Question 6), not as a push-time re-resolution step. If the spike fails (plausible — Docs batchUpdate has no documented "move content range" primitive, confirmed by architecture review), reordering sections silently breaks every existing "See ... (section 05)" cross-reference in the doc, with nothing rewriting them. | A user reorders two sections, pushes successfully (status `ok`), then later notices cross-section links in the Google Doc point at the wrong (or now-nonexistent) heading — no warning surfaced at push time despite the plan's own Observability Plan not listing "cross-section anchors invalidated by reorder" as a distinct status row. | Add an explicit acceptance criterion and status row: "reorder that would invalidate a cross-section anchor" → `warning`, naming the stale anchor — regardless of which go/no-go branch is taken. Do not let this be assumed-covered by the generic reorder-detection row. | P1 |
| 3 | Comment bucketing (Task 4.1.1) uses first-substring-match-in-manifest-order against `quotedFileContent`. Real docs commonly have short, generic, or repeated quoted spans (a one-word heading quoted twice, boilerplate like "TODO" or "N/A" appearing in multiple sections' tables). Architecture review already flagged the *silent-misassignment* case (no warning on multi-match) as a concern, but even with a warning added, the plan never bounds how bad this gets at real-doc scale — with dozens of sections, ambiguous short quotes could become the common case rather than the rare one, producing a comments experience that's worse than today's single-sidecar file (users lose comments into the wrong section silently or get warning-fatigue on every pull). | Users report "my comment disappeared" or "the reply I wrote went into the wrong section's sidecar" during dogfooding; comment counts pulled don't match Drive's comment count for the doc. | Before Epic 4 implementation, run the bucketing algorithm against a handful of real large docs (not synthetic fixtures) and measure the ambiguous-match rate. If it's non-trivial, use quote length/uniqueness plus position-of-first-occurrence-in-doc (not just manifest order) as a tiebreak, or fall back to a paragraph-anchor-based match if the Drive API comment payload exposes one, rather than shipping pure substring matching untested at scale. | P2 |
| 4 | Section-identity-by-`heading_id` assumes Docs preserves `heading_id` stably across edits, but the plan never verifies what happens when a user's edit workflow round-trips through Google Docs UI itself (not just docspan) — e.g., a user manually deletes and retypes a heading in the Docs UI between docspan pulls (not through docspan at all). This is indistinguishable from "section deleted + new section inserted" per the plan's own identity model, which is the correct call per requirements, but it's also the single most common real edit a non-power-user will make to a heading (select text, retype), and the plan's Story 2.2 acceptance criteria only test the *rename-without-position-change* case, not "user deleted the whole heading line and typed a new one" which Docs treats identically at the API level regardless of user intent. | Every time a user "renames" a heading by retyping it directly in Google Docs (rather than editing the local .md file and letting docspan diff detect a rename), the next pull reports it as delete+insert (new file, new `heading_id`, comments reset, manifest churn) rather than a rename — surprising and eroding trust in the feature within the first few real edits. | Document this explicitly as a known limitation in the user-facing docs/CLI help (not just an internal ADR), and add a test asserting the delete+insert classification is intentional (not a bug) for edits made via the Docs UI. Consider whether the `warning`/`conflict` status for this case should say "this may be a rename made outside docspan" to reduce confusion, rather than reading as an unqualified delete+insert. | P2 |
| 5 | `push_sectioned`'s Task 3.1.3 image-path fix (pass one section file's path, not the directory, as `markdown_path`) is correct for the current flat-directory model, but nothing in Epic 3/6 verifies image resolution *per originating section* when different section files reference images with the same relative filename in different subfolders users might create anyway (the plan explicitly says subdirectories are "out of scope for v1" but doesn't prevent a user from making one, since sections are just files in a directory the user can otherwise organize freely) — or more simply, when two different sections both have `./diagram.png` referring to genuinely different images (common when sections were originally independent docs). Because all N section markdown strings get concatenated into one string before parsing (Task 3.1.1), and only one `markdown_path` anchor is used for all of them, two different `./diagram.png` refs from two different original sections collide and one silently resolves to the wrong file. | A push succeeds with `ok` status, but the wrong image appears in one section of the rendered Google Doc — undetectable by any automated round-trip fixpoint test unless that test specifically uses colliding same-named images in two sections, which Story 7.1's fixture list doesn't call out. | Add a fixture case to Story 7.1/7.2 with two sections independently referencing an identically-named-but-different image, and assert push either (a) resolves each image against its own originating section file's path (requires threading a per-node source-file mapping through concatenation, which the plan says is out of scope), or (b) detects the ambiguity and surfaces it as `warning`/`error` rather than silently picking one. | P3 |

- [x] Failure #2 — Addressed: plan.md's Observability Plan gained a "Reorder invalidates a cross-section anchor" → `warning` status row, and Story 7.3 gained an explicit acceptance criterion for it, independent of which Task 3.2.2 go/no-go branch is taken.
