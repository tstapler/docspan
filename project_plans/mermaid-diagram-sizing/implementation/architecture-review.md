## Concerns
- [ ] Story 1.2.1 / Task 1.2.1a — `_make_insert_requests`'s image branch has three mutually exclusive sub-cases (`is_bare_image`, `before_newline`, default-`else`), and the new `updateParagraphStyle` block executes unconditionally across all three (unconditional insert before the shared `continue`, per Task 1.2.1a). Story 1.2.1's three acceptance criteria only cover the default case and the `is_bare_image` case — the `before_newline` case has no Given-When-Then and Task 1.2.1b's test list only names "three cases" matching those three ACs. `before_newline` is real, reachable, node-type-agnostic (set from caller-side structural conditions at `docs_request_builder.py:1603,1664`, not gated on `DocsImageNode`), and no existing test exercises an image through it today (`grep -rn before_newline tests/ | grep -i image` → no hits) — so this is genuinely new, unverified logic in a path with zero prior coverage, not just a redundant test gap. The `paragraph_start`/`paragraph_len` formula for that branch is very likely correct by mirroring the adjacent text-paragraph branch's identical `paragraph_start` formula and matching length semantics, but "very likely correct by inspection" is exactly the class of claim this plan's own methodology (Given-When-Then per branch) is supposed to convert into "verified." **Remediation**: add a fourth acceptance criterion to Story 1.2.1 and a corresponding test in Task 1.2.1b for a mermaid image inserted with `before_newline=True`, asserting the `updateParagraphStyle` range is `{"startIndex": insert_at_index + 1, "endIndex": insert_at_index + 3}` (mirroring the default case's off-by-one, shifted by the leading newline).

## What checked out (no finding)
- **SOLID/layering**: new helpers (`_png_pixel_dimensions`, `_mermaid_image_size_pt`) added to `image_source.py` match the file's existing plain-function style (`_read_local`, `_sniff_mime_type`) and existing `Optional[...]`-return-on-failure convention; no new class, no layer crossed — sizing stays in the adapter module that already owns the rendered bytes, consumed by `docs_request_builder.py` only via the existing `width_pt`/`height_pt` fields it already reads. Alternative 2 (move sizing to the request builder) was correctly rejected: verified the request builder never receives raw bytes today, only `node.src` (a resolved URI) — moving sizing there really would require threading `rendered_bytes` through the node or an extra Drive round-trip.
- **Type-driven design**: rejecting a `PngDimensions`/`PointSize` newtype in favor of plain tuples is justified and correct — each value is produced and consumed once, one function away, with no cross-entity ID-confusion risk (the actual justification for newtypes per the `type-driven-design` skill). The `Optional`-return "null object" pattern for `_png_pixel_dimensions`/`_mermaid_image_size_pt` matches the codebase's existing convention (`_sniff_mime_type`) rather than introducing a new exception type — consistent, not a missed illegal-states case.
- **Determinism/diff-identity**: the single-shared-scale-factor + fixed 2-decimal rounding approach for `_mermaid_image_size_pt` is correctly reasoned against `_node_key`'s `("__image__", alt, width_pt, height_pt)` diff-identity key (verified at `docs_request_builder.py:288-289`) — independent per-axis rounding would risk float drift causing spurious re-inserts on an unchanged diagram; the plan's chosen approach avoids that class of bug.
- **Pattern selection**: Transaction Script for the 3-line scale arithmetic, guard clause reusing `node.mermaid_source` instead of a new `is_centered` field, and Optional-return over a new exception type are all appropriately sized to the problem — no GoF/PoEAA pattern is being forced where a function would do, and no missing pattern was found either.
- **Tech Debt Disposition**: `research/architecture.md` §4's "Extend as-is, no violation" finding is honest — independently traced the actual mermaid-image data flow (`resolve_document_images()` is confirmed the single integration point; `docs_request_builder.py`'s `objectSize` consumption already exists and needs zero changes) and found nothing architecture.md glossed over. The one-row disposition table is sized correctly for a small, single-seam feature.
