# Pre-mortem: mermaid-diagram-sizing
**Date**: 2026-09-18

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | A future edit (or a code path this plan didn't anticipate) skips or breaks the `÷ RENDER_SCALE` step in `_mermaid_image_size_pt()`, so `width_pt` computes to ~1404pt (3x too large) instead of ~468pt — the single highest-risk mistake `research/pitfalls.md` §1 already flagged. | A newly pushed diagram visually overflows the page margins by roughly 3x in the real Google Doc (Story 1.3.4's manual check, or a user report after it ships) — `objectSize` has no page clamp so Docs renders it oversized rather than erroring. | Story 1.1.2's tests already assert the `2400x1200`→`(468.0,234.0)` case and the `RENDER_SCALE`-independence case, but neither is wired into the Phase 6 verification checklist as a *blocking* gate — promote "assert `width_pt` is within Xpt of `CONTENT_WIDTH_PT`, not ~3x it" from the checklist's advisory bullet to a required, CI-enforced assertion (e.g. a bound check `width_pt <= CONTENT_WIDTH_PT * 1.1`) so a regression fails tests, not just a manual doc check. | P2 |
| 2 | `_png_pixel_dimensions()` returns `None` for a diagram whose PNG bytes are subtly non-standard in production (mmdc version drift changing chunk order, a partially-written/corrupted disk cache entry that happens to be ≥24 bytes) — the function was designed to never raise, but a silent `None` means sizing is silently skipped with zero observability (Observability Plan explicitly adds no logs for this path). | A specific diagram (not all diagrams) renders at Docs' tiny default size with no error anywhere — indistinguishable from "feature never shipped" for that doc, and nothing in logs/metrics points a maintainer at the cause. | Add a single log line (not a full metric) when `_mermaid_image_size_pt()` returns `None` for a node that does have `mermaid_source` set — the Observability Plan currently treats this as "near-zero-likelihood, proportionate to skip," but "proportionate to skip a log" and "proportionate to skip detection entirely" are different; a one-line `logger.debug`/`warning` costs nothing and turns a silent gap into a greppable signal. | P2 |
| 3 | The CENTER-alignment `before_newline` sub-case (`paragraph_start = insert_at_index + 1 if before_newline else insert_at_index` in Task 1.2.1a) is explicitly flagged in `architecture-review.md` as untested, and Story 1.2.1's acceptance criteria only worked through the non-`before_newline` and `bare_last` cases — an off-by-one in that branch's range would apply `CENTER` to (or corrupt the formatting of) the *wrong* paragraph, i.e. adjacent user text rather than the diagram. | A doc where a mermaid diagram sits mid-paragraph (not at a clean boundary) shows unrelated body text suddenly center-aligned after a push, or the Docs API rejects the request with an invalid-range error on that specific document shape. | Add the missing `before_newline=True` Given-When-Then to Story 1.2.1's acceptance criteria and Task 1.2.1b's tests before implementation — mirroring the plain-paragraph branch's already-tested `before_newline` handling one line above the new code — rather than leaving it as a known-untested gap noted only in the architecture review. | P1 |
| 4 | The "always-fill" decision (scale unconditionally to `CONTENT_WIDTH_PT`, never cap-only) forces every diagram to full page width regardless of how simple it is — a small, already-legible 3-node flowchart that used to render at a reasonable native size now gets blown up ~2-4x, which for some diagrams exceeds the PNG's native raster detail and looks blurrier/worse, not better, contradicting the Problem Statement's actual complaint ("too small to read comfortably"). | A user reports that a diagram that was already fine now looks oversized, pixelated, or visually dominant relative to surrounding text — the fix overshoots for the subset of diagrams that weren't the problem being reported. | This was a deliberate, documented tradeoff (Unresolved Questions section), not an oversight — but the plan gives no fallback if it's wrong in practice. Add a fast, cheap escape hatch to the Rollback/Risk Control section: since there's no config knob (by design), note that reverting to cap-only is a single-line change to `_mermaid_image_size_pt()`'s `scale` formula (`min(1.0, ...)` or similar) so a wrong bet here is a same-day fix, not a re-plan — and explicitly ask a real user (Story 1.3.4's manual check) to visually judge a *small* diagram's post-fix appearance, not just a diagram that was previously too small. | P2 |
| 5 | A user edits an old doc's mermaid fence (or just re-pushes an old doc) expecting the new auto-sizing to apply, but Story 1.3.3's documented diff-identity behavior means any diagram already in the doc with a previously-committed size is silently never resized — because `_content_key()` for images is `(alt,)` only and `alt` is unchanged, the mismatch folds to "equal" and nothing happens, with no warning surfaced to the user that this occurred. | A user reports "I pushed again and the diagram is still small" as if it's a bug, when it's the intentional (but user-invisible) known limitation — support/triage time is spent re-discovering this documented behavior instead of it being visible at push time. | Beyond documenting the limitation in plan.md (already done), add a push-time warning: when `resolve_document_images()` computes a *different* `width_pt`/`height_pt` than the pulled node already had for a mermaid node, emit a warning (via the existing `ImageResolutionError` residue path) noting "diagram size unchanged — re-insert to apply new sizing," so the silent swallow becomes a visible, actionable message instead of a support surprise. | P1 |

## P1 Items (address before implementation)
- [x] Failure #3 — **Resolved in plan.md.** Story 1.2.1 now has a fourth Given-When-Then covering `before_newline=True` (range `{startIndex: insert_at_index+1, endIndex: insert_at_index+3}`), and Task 1.2.1b's description explicitly requires covering all three paragraph-boundary sub-cases (`is_bare_image`, `before_newline`, default). Cross-referenced to validation.md's `test_mermaid_image_insert_adds_center_paragraph_style_request_when_before_newline`.
- [x] Failure #5 — **Resolved in plan.md.** New Task 1.1.3c (Story 1.1.3) adds a push-time "diagram size may be stale" warning appended to `image_warnings`/`plan.image_warnings`, implemented in `backend.py`'s `_build_push_plan()` (not `image_source.py`, since `current_nodes`/the pulled doc's existing size isn't available at `resolve_document_images()`'s call site — corrected during repair). Does not change the underlying no-op behavior (Story 1.3.3), only makes it visible.

## Summary
2 P1 items, 3 P2 items, 0 P3 items. Top failure mode: the untested `before_newline` CENTER-alignment sub-case (architecture-review.md's own flagged gap) risks misapplying paragraph centering to adjacent user text rather than the diagram, and ships with zero test coverage for exactly the branch most likely to have an off-by-one.
